**Research date:** 2026-10-18. **Status:** options for a future decision; no root license has been selected or applied. This is practical licensing guidance, not a legal determination. It concerns the project-authored tool, not a grant to redistribute ATS, DLC, map-mod, or generated `.scs` contents. Read the [publication review](PUBLIC_REPOSITORY_REVIEW.md), [existing provenance recommendation](OPEN_SOURCE_LICENSE_RECOMMENDATION.md), and [SCS terms research](SCS_MOD_PUBLICATION_TERMS.md) before release.

## What the choice changes for you

Publishing readable source on GitHub would let people inspect it. It would **not** by itself grant the broad use, modification, and redistribution rights associated with open source. There is currently no root `LICENSE`; absent a license, ordinary copyright restrictions remain, apart from GitHub's limited platform permission to view and fork. An explicit open-source license lets others use and sell software commercially. You can still sell your own copies or services; no candidate below promises you income, contributions, bug fixes, or attribution beyond its actual notice terms. The standard licenses include warranty and liability disclaimers, subject to applicable law; none makes you provide updates, support, or compatibility with later ATS releases. A separately agreed support contract or warranty would be your own decision. [GitHub licensing guidance](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository), [GitHub terms on contributions](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service), [OSI MIT text](https://opensource.org/license/mit), [OSI GPLv2 text](https://opensource.org/license/gpl-2.0), [Mozilla MPL 2.0](https://www.mozilla.org/en-US/MPL/2.0/).

The choice is mainly about what **recipients who share their versions** must pass on. None of these licenses requires a person to publish private experiments merely because they modified the code. GPL and MPL source duties arise on distribution; ordinary GPL does not require a hosted service to publish server changes merely because users interact with it over a network. The current tool runs locally, so AGPL's additional network-source rule offers little immediate value. Consider AGPL only if a future hosted service becomes a real part of the project and its rights and compatibility are reviewed separately. [FSF GPL FAQ on private changes](https://www.gnu.org/licenses/gpl-faq.en.html#GPLRequireSourcePostedPublic), [AGPLv3 section 13](https://opensource.org/license/agpl-3.0).

**Concrete example:** if a user changes `map_sector.py` and hands a packaged executable to a friend, MIT and Apache-2.0 do not require that user to disclose the changed source. MPL-2.0 requires source for covered files such as that file, if it was originally MPL-covered. GPL requires corresponding source for the covered program, under its GPL terms, to the recipients. If the same person changes a local copy for personal use and shares nothing, these distribution duties do not arise. The exact scope of a combined work can be fact-sensitive. [MIT](https://opensource.org/license/mit), [Apache-2.0 §4](https://www.apache.org/licenses/LICENSE-2.0), [MPL-2.0 §§3.1–3.3](https://www.mozilla.org/en-US/MPL/2.0/), [GPLv2 §§2–3](https://opensource.org/license/gpl-2.0), [FSF FAQ](https://www.gnu.org/licenses/gpl-faq.en.html#GPLRequireSourcePostedPublic).

## A decision that preserves your options

1. **If the focused review confirms independent implementation from format facts:** choose based on your intended community. The bounded comparison so far found no obvious copied routine; **MIT** is my current policy preference for the project-authored Python if that finding holds, because it makes reuse and community adoption simple. Someone may distribute a closed commercial fork. Choose **MPL-2.0** instead if sharing improvements to your existing files matters more than that simplicity. Choose **Apache-2.0** if its explicit patent grant is valuable enough to justify extra notice work and the GPLv2 compatibility boundary. You may choose GPL for original code as a policy preference; the earlier conservative recommendation is not a claim that every researched file must be GPL.
2. **If protected upstream GPL implementation was adapted:** confirm the exact upstream version grant and copyright notices first. If the applicable grant is GPLv2-only, **GPL-2.0-only** is the straightforward distribution path for the derivative work. MIT, Apache-2.0, MPL-2.0, and GPLv3-or-later cannot simply replace that upstream grant. If the applicable upstream grant expressly permits later GPL versions, reassess the GPLv3 path. If the boundary remains materially uncertain and permissive release matters, obtain a competent rights review or rightsholder permission before making the whole-tool permissive claim. [GPLv2 §§2, 9–10](https://opensource.org/license/gpl-2.0), [ASF on Apache-2.0/GPLv2 compatibility](https://www.apache.org/licenses/GPL-compatibility.html).

For contributions, the easiest initial rule is “contributions under the repository's selected license.” GitHub's terms make that the ordinary default when a repository clearly notices its license. A [Developer Certificate of Origin](https://developercertificate.org/) sign-off can record that a contributor has the right to submit a patch; it does **not** transfer copyright or grant a separate future relicensing option by itself. A contributor license agreement is optional and should be considered only if there is a specific need for broad relicensing or dual licensing; explain its scope before accepting outside code. You can license **your own** code in multiple ways or change its license for future releases, but cannot unilaterally relicense another contributor's copyrighted contribution outside rights they granted. A new license cannot withdraw permissions already granted for copies released under an earlier license. Keep provenance and notices for third-party code under its applicable terms. [GitHub terms §D.6](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service), [DCO text](https://developercertificate.org/), [FSF on multiple licensing and ownership](https://www.gnu.org/philosophy/assigning-copyright.en.html), [GPLv2 §6](https://opensource.org/license/gpl-2.0).

**Before any actual license change:** record the exact source-tree/commit evidence and parser comparison, decide the scope of code versus documentation and icons, and use an unambiguous SPDX identifier plus the appropriate full license text and notices. A tool license would not clear a generated mod archive containing game or third-party map resources. Publication also has separate privacy and artwork decisions in the linked review.
